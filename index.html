Why read_ahead_kb is influential, but not an absolute folio-size cap

Window size is one constraint

In page_cache_ra_order(), allocation order is constrained by the readahead window and the mapping’s supported orders. Alignment, file boundaries, and allocation success can reduce actual sizes. With an ordinary 128 KiB window, 128 KiB fits; 2 MiB does not.

A large read request can extend the window toward bdi->io_pages, derived from max_sectors_kb. POSIX_FADV_SEQUENTIAL also doubles a file’s readahead limit. Therefore, 128 KiB in sysfs is not a universal ceiling. Changing it does not split folios already resident in the cache.

Inspect the filesystem-facing device

Check the md or dm device backing the filesystem, as well as its members. Example read-only checks; replace the path and md0 with the correct names:

findmnt -no SOURCE,FSTYPE --target /path/to/journal
cat /sys/class/block/md0/queue/read_ahead_kb
cat /sys/class/block/md0/queue/optimal_io_size
cat /sys/class/block/md0/queue/max_sectors_kb

The two _kb values use KiB; optimal_io_size uses bytes. A default of 128 KiB is a baseline, not a guarantee for every disk.

The app changes 64 bytes

With pwrite(), the kernel receives an offset and length, then copies 64 bytes into the page cache. With a shared mmap, the CPU stores directly into the mapped cache memory. An initial write fault lets the filesystem prepare the mapping for writes.

Both update cached file data in RAM. Neither ordinary operation promises that the data is already durable on disk.

Timing, dirty state, and what this example leaves out

dirty_writeback_centisecs controls periodic wake frequency; dirty_expire_centisecs supplies the age cutoff for old-data selection. The first dirty inode may schedule delayed work via wb_wakeup_delayed(). Age is an inode scheduling heuristic, not a timer attached to each modified byte. Dirty-pressure writeback, reclaim-related work, and explicit sync requests may cause I/O sooner.

A folio dirty flag and iomap’s per-block dirty bitmap are different things. Both paths mark the folio dirty; their block maps differ. Buffered writes track the range copied, not a comparison of old and new byte values. Counts here are file-data writeback bytes, excluding filesystem metadata and journal traffic, and SSD-internal writes. This model uses ordinary buffered I/O and shared mappings, not DAX, direct I/O, or MAP_PRIVATE.

Why random and maximally scattered are different

With 512 full-block updates, the app changes only 2 MiB. The initial random sample touches 317 large folios: 634 MiB of mmap writeback versus 2 MiB with write(). Confining the same amount of work to 16 MiB touches eight 2 MiB folios. Placing one update in every 2 MiB region touches all 512: 1 GiB versus 2 MiB. That last pattern is a deliberately spread example, not the expected outcome of every random workload.

These counters are computed from the selected offsets. Repeated modifications before a flush can coalesce. A later modification after a completed flush can cause the same folio to be written again.

03 / TWO DIFFERENT GRANULARITIES

A folio is not
a page-table entry.

The page cache groups file data into folios. Page tables map virtual addresses to that memory. A large cache folio can be reached through either small or huge mappings.

CPU PAGE TABLES · TYPICAL x86-64 SIZES
1 PMD entryOne dirty bit covers 2 MiB
↓
PAGE CACHE · SAME MEMORY IN BOTH CASES
One 2 MiB folio512 filesystem blocks · modeled mmap writeback: 2 MiB

A PMD dirty bit says that something in its 2 MiB mapping was written. It does not identify the modified 4 KiB block.

Mapping size changes what the CPU can report.

A 2 MiB folio does not guarantee a PMD mapping. The fault path checks size, alignment, page-table state, and mapping policy. Smaller PTE mappings are used when a huge mapping cannot be installed.

In the whole-folio dirtying behavior modeled here, PTE-mapped large folios can also suffer the amplification. Selecting PTEs alone does not fix the filesystem’s dirty tracking. Buffered write() gets its precision from the supplied offset and copied length, recorded in iomap’s dirty-block bitmap. It does not depend on PTE dirty bits.

Where finer tracking could help

PTE dirty bits provide 4 KiB information in this example. A September 2026 RFC proposed harvesting them for sub-folio dirty tracking. PMD mappings still expose only a coarse dirty bit. This page illustrates the behavior motivating that work; it does not claim the RFC is merged or enabled on your kernel.

Where the large folio came from

The readahead profiles above show the setup stage. A wider window can accommodate larger folios before the writes begin. This mapping diagram specifically shows a 2 MiB folio; the 128 KiB profile uses smaller cache folios, which are PTE-mapped in this x86-64 example. Real files can contain mixed sizes.

What tells writeback which blocks to send?

Same 2 MiB cache folio, same 64-byte edit within one 4 KiB block. Whole-folio mmap dirtying is the behavior modeled here.
